计划标识：YD-N1；当前需求修订：R1（2026-10-11）。全部开发阶段待用户启用。本轮是在原#23—#37内补齐需求，不换阶段、不新增计划、不恢复已撤销Issue，不把需求修完写成系统已实现。
当前执行依据为本单、#24—#37当前正文及本计划有效决定。依据用户最终对话；本轮按用户“没有接着修，修完再审”指令落实三方一致性审计。四份对照文件只用于定位缺失/差异，只有明确写入当前正文的条款纳入；旧编号、旧API样例、指定医生/首选工位、跨能力抢选、全员病历读取、保存即计费等不恢复，也不要求Codex回读旧计划补规则。
仓库Yredxin/YDental；目标Project #4。已有代码/环境只按当前实际重新盘点，不自动继承历史业务设计。

## 1. 项目背景
以Odoo 20 Community为目标建设多门店牙科业务系统，连接员工、空间、供给、患者、治疗检查、物资、结算、复诊、人工外加工和打印报表。Ubuntu odoo-sd为工作区，自研插件在实际sd-addons仓库；odoo-12学习环境不动。具体核心提交和依赖由S00核实，不照历史报告认定。
用户决定需求、具体任务启用、生产配置和效果验收；Codex实现被启用范围、测试并在GitHub交付；GPT在用户请求时读GitHub复核并回写。无需用户搬运整份报告，不部署双方后台自动唤醒。

## 2. 需求背景
同人跨店权限不同，区域预约不能绑定个人医生；排期提供供给但实际坐诊可变化。外检可以保留原椅或交还区域，患者不能同时排多个有效队列或实际双处执行。文书实时保存与执行确认分开，价格、库存、费用、款项和文书可追溯，断网/跨日/部分检查发药/取消更正都有明确出口。
按先功能、后统一美化推进，阶段均有八部分。任务标题完整不等于需求无遗漏，测试条目多不等于实际通过；本轮同时补需求、示例、测试和验收材料。

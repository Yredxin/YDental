## 2. BLOCKER-1：处方/椅旁来源类别没有在库存服务端强制匹配物资类别

固定代码：[service.py L408—426](https://github.com/Yredxin/YDental/blob/f23ad62b20aa298b74adc993781863961946aec3/ydental_inventory/models/ydental_inventory_service.py#L408-L426)。

`_source_action` 对 `kind` 只验证是 `treatment/chairside/prescription`，再验证medical/pharmacy权限和当前门店lot；但 `_lot` 仅要求该商品具有**任意** `ydental_inventory_kind`。之后 `self._location(config, lot.product_id)` 会依商品类别选择库位。因此，按当前代码，受控 `prescription` 来源配合有库存的 `material` 或 `prosthesis` 批次，或者 `chairside` 来源配合非medicine批次，存在被当作合法药品执行扣库的路径。此处不需假设可伪造产品默认私有hook；仅是**将来合法hook以及当前受guard合成来源**传入“来源类型×物资类别不匹配”时，缺少服务端最后一道边界。

定向修正：在可信来源payload取得、权限验证后、任何event/move创建前校验类型×真实产品类别。处方带走药与椅旁药品必须是 `medicine`；治疗耗材等其它组合按#31真实语义定义，不擅自开放不相容类型。独立模型/合成来源负向覆盖 pharmacy-write+material/prosthesis prescription、medical-write+非medicine chairside；均应完整拒绝且event/move/quant/audit无变化。保留合法medicine 处方/椅旁、治疗耗用、重复来源/权限回归。未来S08不能只依赖UI过滤或上层hook来保证。

## 3. BLOCKER-2：真实已发生事件的待核对恢复受“现在的过期/停用”误阻断

固定代码：[service.py L253—277](https://github.com/Yredxin/YDental/blob/f23ad62b20aa298b74adc993781863961946aec3/ydental_inventory/models/ydental_inventory_service.py#L253-L277) 与 [L429—438](https://github.com/Yredxin/YDental/blob/f23ad62b20aa298b74adc993781863961946aec3/ydental_inventory/models/ydental_inventory_service.py#L429-L438)。

`_event(actual=True)` 容许已实际发生但账不足/批次不可用的真实来源进入pending，保留事实；然而 `_recover` 对任何pending都先执行 `_usable(event.ydental_lot_id, store)`，它按**当前**产品/batch启停与**当前**效期判定。即使随后凭真实入库/盘点纠正库存，只要该批次已经过期，就不能补记原执行；若在实际治疗后批次被停用，同样无法恢复。这混淆了“禁止新的过期/停用执行”和“记录历史真实耗用事实”，导致#31要求的原事件核对恢复可能永久卡住。

定向修正：严格区分新执行的当前可用性校验与已有 `pending` / already-performed 原事实恢复。仅对原有不可变真实来源、已授权责任人、真实库存纠正/证据和可用余额满足的情况走受控历史补账，冻结原事件ID、批次、数量、原价版本、责任人/实际时间与审计；不得修改lot效期或假启用批次来闯关，不得伪造入库/临床事实，不得允许过期/停用批次发起新的执行。区分执行时与补记时、无法确认来源真实性/数量时保持pending并给出人工核查出口。任何解除 `_usable` 的代码只允许发生于严格的**原pending补账**路径，不能开放普通issue/处方/退回release。

至少新增：①有效批次曾发生真实事件但缺料pending→时间跨到过期→真实纠正→同原事件唯一recover；②pending之后batch被停用→有证据纠正→同原事件唯一recover；③同状态下新的普通/临床执行仍拒绝；④异常/并发恢复仅一个原move、无半账、原价格快照不变。补足model、必要HTTP及真实独立连接竞争/负向断言，并确保S07-F3/T06仍成立。

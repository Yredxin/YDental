## Error codes and privacy

Codes are fixed constants or a typed exception attribute, not translated-message parsing. INPUT_PARSE_ERROR belongs only to the request conversion block. AUTHZ_DENIED covers ordinary AccessError, INPUT_REJECTED covers ValidationError, BUSINESS_RULE_REJECTED covers other expected UserError; order must account for subclassing. A TypeError/KeyError arising inside the service is APPLICATION_ERROR even if the existing UI response stays 409. An unexpected exception propagates exactly as before and is logged with a controlled sanitized stack. Known detailed codes use typed subclasses at their original raise sites with unchanged exception text.

Framework/core exceptions that cannot be reliably classified more specifically receive the stable coarse code with `reason_detail=UNCLASSIFIED`; no code is fabricated. Missing mandatory audit triggers the current transaction exception behavior and never becomes successful business completion. Logging exceptions are isolated from business code, mark diagnostic failure, and cause the supervisor to stop further writes before the next dispatch; they cannot cause replay.

Error event contains type, trusted code, sanitized frame filename/function/line, root_event_id and a private stack_ref. Exclude locals, arbitrary exception messages, raw payload, SQL arguments, full URLs/query strings, content, name/login and tokens. If an exception message is not a static recognized template it is omitted. Public evidence exports only whitelisted synthetic references after automatic sentinel/control-character scan and independent human review; hash consistency is not proof of truth. Newlines and other untrusted strings serialize as JSON string escapes and have length limits.

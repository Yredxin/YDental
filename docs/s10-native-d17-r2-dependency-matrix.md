## 配置闭包扫描结果及边界

对本表涉及的YDental模型目录检索`ir.config_parameter/get_str/get_param/configuration_required`：实际相关读取为S06队列heartbeat与timeout；`ydental_access.manager_policy`只在经理任免/离职路径，当前三人授权不调用；`ydental_space.svg_max_bytes`仅空间SVG上传，本夹具不上传；S07仓库缺失由`_config`拒绝、S03政策缺失由`_select_policy`拒绝、S06 missed-limit由area字段守卫、S05正式价格政策仅显式`demo_confirmation`、患者编号要求真实sequence。这是自研源码范围内的静态闭包，**不证明Odoo原生warehouse/product/HR/mail/stock运行时没有其它配置读取或文件副作用**。上两次失败说明原私有夹具未把测试辅助的显式S06配置纳入依赖图；后续不得用“没有静态发现”替代实际后验核验。

## 未来预算与可证伪性

本批未使用原R1剩余B配额。仅在另获正式授权且前置矩阵/未决副作用审核通过时，建议**一座全新**纯合成库：CREATE≤1、准备Odoo≤1、两个独立GDB只读shell≤2，绝不复用失败OID2100087/2100096。准备后要证明唯一event↔fee↔S05快照↔S07 done move，原生account.move/payment/partial和S10交易表/mail_mail均0，每个新增filestore文件可追溯；否则STOP。两个只读shell只比较registry重叠与真实signal11/C栈，不执行临床或结算actor。原SIGSEGV发生在actor动作前；L2状态仅增加事故前置相似度，无法单靠未复现排除Native内存故障。若无法审计原生/文件副作用或再次遇基本配置缺口，应暂停L2复现方向，先做S05×S07真实业务兼容问题的独立授权和产品级测试。

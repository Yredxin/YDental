# 如何操作、填写与保存

1. 把完整手册解压或复制到**私有副本**，保留目录结构。先读[环境清单](environment-and-data.md)及[验收计划](acceptance-plan.md)；环境或数据未准备好时保留 NOT_RUN，必要时记录 BLOCKED 和原因。用户不需要创建账号、数据库或运行 Docker 命令。
2. 从[总入口](../README.md)按岗位、场景或功能进入用例，先与环境负责人确认产品版本、门店、实际权限和逻辑对象对应的合成数据。执行依赖按计划及用例前置；同一业务来源不得重新提交，不同独立合成对象可依前置执行同一用例。
3. 每次执行在用例“用户填写区”复制一份执行记录，按该用例分配唯一 RUN-ID，例如 `RUN-UAT-FIN-002-001`，下次使用 `RUN-UAT-FIN-002-002`。分别登记日期、版本、环境、岗位、门店、逻辑对象、浏览器、CSS 视口宽高和缩放。桌面、平板、手机和修复后复验分别使用新 RUN-ID；保留旧 RUN。
4. 逐步记录实际动作与可见结果，并填 NOT_RUN / PASS / PARTIAL / FAIL / BLOCKED / N/A。状态未知、数据不一致、权限异常或来源无法唯一识别时，立即停止受影响动作并联系负责人核实，不盲目再提交。
5. 一个 RUN 可有多个问题。每个问题复制原用例的问题记录，分配全套副本唯一的 `UAT-ISS-0001` 等 ID，填写位置、前置、首次发生步骤、预期和实际、已安全观察到的复现步骤、稳定性、P0–P3、功能/UI/需求/环境分类、截图与阻断情况；在[问题汇总](../40-results/issues.md)只引用原记录。不要为了记录或复现而重新做一次已提交的收费、治疗、库存或退款。
6. 在每个 RUN 的 UI 意见中分别记录信息布局、操作流程、字号可读性、间距颜色按钮、三档差异、原因及期望调整；标记“必须修改 / 希望优化 / 可接受”。[UI 汇总](../40-results/ui-feedback.md)引用原 RUN；UI 偏好不自动改变业务规则。
7. 每个 RUN 使用自己的截图目录。例如在 `30-functions/settlement/cases/UAT-FIN-002.md` 中，手动在对应 `images/UAT-FIN-002/` 下创建 `RUN-001`，引用 `![步骤3：用途](../images/UAT-FIN-002/RUN-001/03-用途.png)`。文件命名为“步骤编号-用途-可选序号.png”；原始图和失败图保留，标注图另存，新一轮不覆盖旧图。
8. [阶段登记](../40-results/stage-status.md)、[问题](../40-results/issues.md)、[UI 意见](../40-results/ui-feedback.md)、[复验](../40-results/retest-register.md)和[需求反馈](../40-results/requirements-feedback.md)引用用例、RUN 和问题 ID；最终填写[用户结论](../40-results/final-review.md)。可先看[明确标记的虚构填写示例](example-run.md)，它不计入任何真实结果。
9. 填写材料和截图只放私有副本。交给用户指定的 GPT/Codex 时保留整个目录和相对路径；如将来需要同步公共仓库，先检查是否包含真实患者、账号、口令、Session 或未经授权的财务、临床内容。

任何持久提交结果不明时，先停止并核实；不要为了截图重做。环境负责人准备合成策略和账号，用户无需操作数据库或基础设施。

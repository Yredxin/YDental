## 2. 目标与本次精确范围

### 2.1 正常使用目标

普通有权岗位进入既有结算页面，能看懂“正在搜索谁、实际选择了谁、下面费用属于什么范围”，按姓名或业务号查找、选择患者，阅读原有费用和待核对原因。查看不会自动出账、收款、退款、生成原件或改变责任。

本次将路线表中的“只读摘要”具体限定为**现有三段费用概览**，不是新建财务统计卡片或整个结算页重排：

1. 今日未出账费用。
2. 历史未出账费用。
3. 待核对，禁止出账。

已出账未付清、已结清账单、实收实退及日结等下方区域继续保持；不把它们作为P5顺带任务。这是按区域逐步实施，不代表这些功能被取消或已统一完成。

### 2.2 代码与DOM边界

目标：`ydental_settlement/views/ydental_settlement_templates.xml`中的`ydental_settlement_page`。

**起点**：`section.o_ydental_access_search`，包含Patient lookup、GET搜索、候选患者列表和搜索分页。  
**中间**：已选患者编号提示、原“查看其他门店欠款最小摘要”链接、上述三段只读费用表及其原生追溯/既有分页。  
**终点**：三段费用后、首个`details[name="settlement-operation"]`（`Select fees to bill`，`operation=bill`）**之前**。

允许对这一连续区域增加独立wrapper、语义标记、局部排布、空态说明、必要英文源／zh_CN与一个局部SCSS资源。建议作用域`data-dl-scope="settlement-lookup"`，可在其内分别标记search、selected-patient、fee-overview；wrapper必须在首个办理details前闭合，不能把后面的办理表单包进去。

当前搜索本来是“输入＋结果链接列表”，不是select：继续用这套正常列表，不为统一外观新增下拉、自动补全、实时搜索、弹窗或复制P4选择器。**本阶段默认且计划内不新增产品JS**，也不为此加载后台整包资源或重构共用布局。

## 3. 设计与交互要求

### 3.1 患者查询

- 保持`GET /ydental/settlement`、`q`和`maxlength=100`；按钮及原生Enter明确发起搜索。输入、失焦和移动焦点不触发额外查询，不预取患者资料。
- 主操作只有“搜索患者”；候选项采用普通可聚焦链接，姓名与业务患者号同时可辨。同名以已有业务号区分，不增取电话、证件、病历或全库信息。
- 原候选结果来自`patient_options['rows']`，原顺序、查询范围及分页不变；不在浏览器重新排序、去重、合并患者或缓存全部记录。
- 保留`patient_search_url()`生成的上一页／下一页链接和`has_more`条件。没有真实总数就不增加“共X人／X页”，不把当前页数量称总数。
- 可增加准确的首末边界文字及区内ARIA标签，不制造`href="#"`的假按钮。空态只描述本店当前授权查询没有匹配候选，不透露其他店或无权患者的存在性。

### 3.2 搜索词不等于已选患者——必须保持原请求契约

当前控制器把`q/search_page`交给`_patient_options()`，把`patient_id`单独交给`_workbench()`。二者必须区分：

|动作／字段|本阶段要求|
|---|---|
|搜索框里正在输入的q|只是一份待提交查询；不能改已选编号或下方费用说明|
|搜索GET|原form只提交q，没有patient_id hidden；沿原规则重新进入未选患者的工作台范围，不偷偷保留原患者|
|点击候选|保留既有`/ydental/settlement?patient_id=<真实ID>`链接；原来不带q、search_page及各费用页码，不自行追加或伪造“返回筛选”能力|
|候选分页|直接使用原`patient_search_url()`，保留原q、search_page及已有patient_id参数语义|
|费用分页|直接使用原`page_url(category,page)`，保留当前patient_id、q/search_page及其他分类页码；不手拼链接丢条件|
|已选患者|只依据服务返回的`patient`，不是候选第一项、q文字或前端高亮|

可以在本区域显示“当前未选择患者”或“当前所选患者编号：…”，并说明搜索用于查找候选，选择结果后才按患者查看。**费用范围说明必须在W0核实`_workbench()`实际返回语义后给出**：不得把未选患者时的门店范围列表标为某个搜索结果的个人账务，不以“无匹配患者”推断下方费用为0。不得为了让页面顺眼而清空、隐藏或重算原服务返回的费用。

不新增患者姓名查询或身份API；现有已选编号原值保留，显示范围只使用已授权上下文。原其他门店最小摘要链接的条件、patient_id及地址保持；它只是既有只读入口，不代表拥有他店办理权限，不在P5重设计其目标页面。

### 3.3 三段只读费用概览

先形成字段映射，保持以下当前来源：

|区域／字段|冻结的原投影|
|---|---|
|today/history项目|`fee.ydental_event_id.ydental_catalog_id.name`|
|患者业务号|`fee.ydental_patient_id.ydental_number`|
|确认金额|`money(fee.ydental_amount, fee.ydental_currency_id)`；沿原币种和精度，正负号不改|
|业务日|`fee.ydental_event_id.ydental_business_date`，不改为浏览器日期或录入时间|
|费用追溯|fee.id、fee.name、event.id，保持全部值、原转义和只读含义|
|pending项目与患者|event对应catalog及patient业务号|
|pending业务日／实际执行人|event业务日及actor.name，不替换为当前登录人|
|pending原因|原`ydental_pending_reason or '待核对'`；“待核对，禁止出账”默认可见|
|pending追溯|event.id及event.name，原值不删|
|三段分页|原`page_counts/pages/page_url`和共享页码模板逻辑，原50条门槛保持|

“未出账费用”不是“当前应收”，“确认金额”不是“已收款”；“待核对”不等于金额0或已完成。不要新增总应收、实收、实退、净收入、负债等计算，不对当前页金额求和充当全量汇总，不跨币种合计，不用当前目录价重算已确认费用。

三个区保持独立，不折叠成只有一个总卡片。所有返回行、顺序、来源与分页保持；空段只写本范围／本页暂无对应记录，不写“患者无欠款”“全部结清”。原生details可继续展开追溯，不触发业务请求、不插入执行链接。

## 6. 正常流程

**P5-F1 搜索与选择**：普通有结算读取权角色正常登录选店 → 原菜单进结算 → 输入业务号或姓名并搜索 → 从候选链接明确选择 → 核服务实际selected patient → 查看三段费用与待核对原因。搜索没有候选不代表门店没有费用。

**P5-F2 分页与回访**：使用既有有足够数据的授权候选/费用集合 → 原分页 → 核参数和结果 → 浏览器返回 → 选择另一个既有患者。不能改分页大小或生成业务造多页；真实数据不足时真实一页＋明确纯渲染/回滚夹具，分别报告。

**P5-F3 只读和能力保留**：展开费用追溯；必要时只读进入原其他店最小摘要再返回。观察原办理入口保持、展开一个既有办理details后不填不提交并用原取消链接返回；只验证能力未被误隐藏，不执行新正向经济动作。

**P5-F4 边界与阅读**：普通无源/跨店目标按原后端拒绝；窄屏、长原因、键盘横读与放大可读。缺真实非空样本的某一段用明确组件/回滚夹具核展示，不修改旧事件、确认费用或责任来制造样例。

## 2. 目标与精确范围

仅修改 `ydental_operating_report_page` 中的：

```text
<form action="/ydental/reports" method="get" class="o_ydental_reporting_filters">
    ……当前查询字段、查询按钮及既有切指标说明……
</form>
```

允许为此表单添加局部wrapper、标签、帮助／错误／忙碌状态、专用资源和必要英文源／zh_CN翻译。浮层可挂到body，但只响应本表单实例和专用portal作用域，不形成全站组件替换。

## 3. 设计与交互契约

### 3.1 视觉与流式布局

沿用A“杏陶暖白”、舒展、较大正文。参考既有设计规范和已验局部值：surface `#FFFBF6`、paper `#FFFEFA`、正文 `#382F28`、次要字 `#716359`、主色 `#94513A`、hover `#7E432F`、必要控件边界 `#9C8776`、focus `#6C513F`。

采用表单局部Grid／Flex、`minmax(0,1fr)`及相对尺寸；字段和长标签自然撑高。基准正文1rem、行高1.6、控件min-height约2.75em、区块padding约1.5rem／窄屏1rem。不能改全站html字号，不能缩整页、固定高度截字、隐藏重要条件或用overflow:hidden掩盖根溢出。

每个字段有清楚的可见中文标签。查询为主要按钮；选择器不做一排实色主按钮。候选、选中、焦点、禁用、必填错误和忙碌分别表达，不单靠颜色。实际computed和邻接背景核文字≥4.5:1、必要控件边界／焦点≥3:1；这是局部验收目标，不是全站无障碍认证。

指标／日期可组成第一组，授权范围和适用条件组成第二组；分组不得改变DOM逻辑顺序、字段来源或请求含义。窄屏单列，长门店名＋时区完整可达，不能改业务名称配合排版。

### 3.2 单选增强

指标、法人、适用币种和状态使用同一局部单选实现，不各写一套。优先复用锁定Odoo的组件／Interaction、定位、文本和焦点能力，以及P1已验证的交互契约；不新增外部UI框架。不得为了复用重构或改变P1组件；必要本表单适配在reporting模块内完成，不复制整页业务代码。

原native select仍是唯一具名提交字段，增强触发器无name；成功初始化后才隐藏原控件，禁JS或初始化失败仍可用原native表单。保持option空值、disabled、selected及原候选集合；不把展示标签改成提交值。

键盘上下／Home／End只移动候选，不提交请求；Enter／Space确认，Esc取消；Tab／ShiftTab确认并自然离开，**指标的确认若真的改变值，则按既有change导航规则处理**。打开、悬停、移动、Esc取消或再次确认同值不能发出指标查询。aria名称、expanded、controls、selected、active、required、invalid与实际焦点保持一致。

长中文、长拉丁串、窗口边缘、滚动、缩放下浮层完整可读。复用实际定位能力，必要时使用视口内浮层和局部滚读；不缩字或截掉选项。滚动和关闭行为要稳定，不陷住Tab、不吞外部点击、不保留失效portal。

### 3.3 门店多选：可见勾选，不新造范围

用语义fieldset／legend和原生checkbox交互增强现有multiple select。勾选项展示原store label与timezone；不新增门店查询，也不让无权门店进入DOM。长列表可在本字段内部滚动，末项与勾选状态键盘可达。

增强checkbox不带会与原字段重复的name；原multiple select是store_ids提交唯一来源。每次勾选同步对应option.selected，提交每个所选store_id恰一次，沿现有GET repeated参数与后端getlist处理。不同时再提交同名CSV hidden值，不丢多选、不静默只保留最后一个。

Space切换checkbox、Tab自然遍历；点击标签可操作。勾选本身不请求报表、不切换用户工作门店。允许显示“已选N家”作为当前选择反馈，N来自真实勾选，不是新报表统计。

0项时应由required校验拦截查询，显示“至少选择一家已授权门店”，焦点到可见可操作位置；不能因为隐藏required的原select而卡死，也不能静默回填默认店骗过校验。没有候选时准确表达范围不可用，不把无权解释成全系统没有门店。

不新增全选／反选／保存常用范围／跨公司自动联动。公司与门店非法组合继续由既有后端拒绝，不为得到200静默删除用户已选条件。

### 3.4 指标切换保留既有语义，避免双重提交

原`reporting.js`在metric的change事件中立即GET导航，仅携带metric/date_from/date_to。保留此契约：更换指标保留日期，门店恢复当前店，清除法人／币种／状态和原页码。普通查询继续使用原revision；不要把指标导航改成另一种参数或认证策略。

增强层仅在确认不同metric时发一次change，由唯一既有处理路径导航。不得旧listener与新listener各发一次，不在候选高亮时触发，不新增定时查询。

表单内明确保留／整理说明：“更换指标后将重新查询，恢复当前门店并清除法人、币种和状态条件。”其他条件调整后由“查询”按钮提交，不在每次勾选门店或选择法人时自动查询。

非金额指标的新页面沿服务器`options['money']`不渲染currency；状态候选沿`options['states']`。不能用隐藏CSS保留错误提交字段、旧候选或自行猜测状态依赖。

### 3.5 草拟条件与已生效结果严格分开

表单中尚未提交的修改不代表下方现有结果已刷新。可以在表单内增加简短说明：“更改条件后请查询；下方结果、导出和钻取按上次已生效条件。”不改结果区本身。

**不要把尚未提交的新控件值写入导出表单hidden字段、分页URL或钻取链接。**这些继续由服务器对已生效结果生成，必须与画面上的那次结果对应。只有正常查询返回新页面后，才使用新的已生效条件。

查询忙碌不得提前报成功；仅在有效submit后禁用必要的无name按钮／交互触发器，不能disabled实际需要提交的字段。恢复页、取消导航或BFCache返回后不得永久busy。前端错误与后端403／409分开，不用客户端预拦截冒后台拒绝。

### T03 单选真实交互

正常页面各适用单选的打开、方向键／Home／End、确认、Esc取消、Tab／ShiftTab、选中与焦点、长选项完整可达；原select具名值唯一。指标与其他单选的提交时机不同，按契约分别实测。

### T05 指标切换与初始化

确认新指标仅一次原change导航，日期保留且范围／实体／币种／状态／页码按既有方式重置；Esc及同值确认无查询。新listener与旧listener不重复，往返／重新初始化不多绑定或残留portal。

### T06 条件适用性与已生效范围

### T07 响应式与长文字
